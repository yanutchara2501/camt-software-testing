# Step 05 - Continuous Integration and quality gates

Branch: `step/05-ci`

## Idea: CI is only the person who presses the button

The logic stays in the repository as `npm` scripts. The pipeline (`.github/workflows/ci.yml`) just calls them, so the
same commands that I run on my laptop are the ones that run on every push.

```
unit  ->  integration  ->  e2e
 (fast, no Docker)   (Postgres)    (whole system, slowest)
```

## Part A - Reading the pipeline

1. **Order of the stages.** Cheapest first: unit (seconds, no Docker) -> integration (needs Postgres) -> e2e (needs the image).
   If a unit test is red there is no reason to pay for the other two. This is *fail fast*, and it also saves CI minutes.
   `needs:` in the workflow enforces the order.
2. **Where Liquibase runs.** Inside the npm scripts (`db:migrate:test`, `db:migrate:e2e`). The database is a fresh container on the
   runner; it lives in `tmpfs` and disappears with the job, so every run starts from an empty database built from the migrations.
3. **Other CI systems.** The same scripts work on GitLab CI (with `docker:dind`, so the DB host is `docker` and not `localhost`)
   and on Jenkins (the agent keeps state between builds, so a `docker compose down -v` in `post { always }` is needed to clean up).
   I only wrote the GitHub Actions version because that is where my repository lives.

## Part B - Seeing CI red and green

The workflow file is written, but it only runs after the repository is pushed to GitHub. I could not do that from here,
so I verified the **same commands** locally: `npm run typecheck`, `npm run test:coverage`, `npm run db:test-rollback`,
`npm run test:integration` and `npm run test:e2e` all pass.
(Pushing and looking at the Actions tab is the first thing to do when the repository goes to GitHub.)

## Part C - Quality gates

### C1 Coverage gate for unit tests

* Script: `npm run test:coverage` runs the unit project with `--coverage`. The HTML report goes to `coverage/` and CI keeps it as an artifact.
* The threshold in `jest.config.js` is set **only for the folders where unit tests are the right tool**:

  | Folder | Threshold | Measured now |
  |---|---|---|
  | `src/domain/` | 100% everything | 100% |
  | `src/services/` | 90% statements/branches/lines, 100% functions | ~96% |

* **Why not a threshold for the whole project?** The unit run covers only ~37% of all statements, because `src/routes/` and
  `src/repositories/` are 0% in the unit project: they are verified by component and integration tests (HTTP, SQL).
  A global threshold would push me to write mock-heavy tests for code whose real risk is in the wiring and SQL.

### C2 Test that every migration can be rolled back

* Script: `npm run db:test-rollback` = reset the test database, then Liquibase `update-testing-rollback`
  (update -> roll everything back -> update again). CI runs it in the integration job before the integration tests.
* Experiment: I changed `--rollback DROP TABLE votes;` to `DROP TABLE vote;`. The script failed with
  `table "vote" does not exist` and exit code 1, so the pipeline would have gone red. I reverted the change.

## Discussion

**Does 100% coverage mean there are no bugs?** No. Coverage only says which lines ran, not whether anything was *checked*.
The smelly test from step 02 had no assertion in one case, and it still counted as coverage. A mutation (changing the code and seeing
whether a test goes red, like I did with the checksum weight) is a better question than "how many lines ran".

**Should a slow e2e run on every push?** If e2e took 15 minutes I would run it only on `main`, nightly, or sharded in parallel,
and keep unit + integration for every push. Today the whole suite is small, so it runs on every push.

## Concepts used in this step

* **Continuous integration**, fail-fast stage order
* **Pipeline as code** that only calls project scripts (same result locally and in CI)
* **Quality gates**: coverage threshold on selected folders, migration rollback test
* **Coverage is a measure of what ran, not of what was verified**
