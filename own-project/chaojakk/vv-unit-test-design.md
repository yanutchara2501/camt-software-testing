## ทำไมเลือกฟีเจอร์นี้

- เป็นด่านแรกของทุกบัญชี ถ้าพังหรือมีช่องโหว่ คนอื่นเข้าบัญชีแอดมินหรือผู้ให้เช่าได้
- มี "ตัวช่วย" (collaborator) หลายตัวที่เราต้องจำลอง ได้แก่ ฐานข้อมูล, การเช็กรหัสผ่าน, การออก token, บันทึก audit, ตรวจรหัส TOTP จึงได้ใช้ stub / spy / mock ครบทุกแบบที่โจทย์ต้องการ
- มีทั้งทางสำเร็จและทางล้มเหลวหลายแบบ ทำให้ออกแบบเคสได้ชัด

## 2.1 ออกแบบ unit test

### หน่วยที่ทดสอบ

| หน่วย | หน้าที่ | ตัวช่วยที่ต้องจำลอง |
|---|---|---|

### เทคนิคที่ใช้ออกเคส

| เทคนิค | ใช้ตรงไหน | ทำไมเลือก | ช่วยการเทสยังไง |
|---|---|---|---|
| Equivalence partitioning (แบ่งกลุ่มข้อมูลที่ปฏิบัติเหมือนกัน) | ตัวระบุตัวตนที่ผู้ใช้พิมพ์: อีเมล, เบอร์มีขีด, เลขบัตร 13 หลักมีขีด (UT-L9 ถึง L11) | ผู้ใช้พิมพ์ได้หลายรูปแบบ แต่ละรูปแบบเข้า query คนละทาง | เทสแค่ตัวแทนของแต่ละกลุ่ม ไม่ต้องไล่ทุกค่า เคสน้อยแต่ครอบคลุม |
| Boundary value analysis (ค่าที่ขอบ) | อายุ challenge 5 นาที: UT-L14 เช็กว่าหมดอายุที่ 5 นาทีพอดี ส่วน UT-R4 ลองใช้หลังหมดไป 1 วินาที (10:05:01) ต้องถูกปฏิเสธ | บั๊กชอบอยู่ตรงขอบ | จับ bug ที่ตัวเลขอายุเพี้ยนไปได้ (ยังไม่ได้เทสที่ 10:05:00 พอดี ถือเป็นช่องที่เติมได้ภายหลัง) |
| Decision table | ผลของ login ตามรหัสผ่านถูกไหม / บัญชี active ไหม / เปิด 2FA ไหม (UT-L1, L4, L8, L13, L15) | มีเงื่อนไขหลายตัวผสมกัน | เห็นว่าเงื่อนไขชุดไหนยังไม่มีเคส |
| State transition | challenge: ใหม่ -> ใช้แล้ว / หมดอายุ (UT-R1 ถึง R4, R6) | challenge ใช้ได้ครั้งเดียว | บังคับให้คิดว่า "ใช้ซ้ำ" ต้องเกิดอะไร |
| Error guessing (เดาจุดที่พลาดง่าย) | ตอบข้อความเดียวกันทั้งเมื่อไม่มีผู้ใช้และรหัสผิด (UT-L6); เช็กรหัสผ่านแม้ไม่มีผู้ใช้เพื่อให้เวลาตอบเท่ากัน (UT-L7); audit ต้องเก็บ hash ไม่เก็บอีเมล (UT-L5) | เป็นเรื่องความปลอดภัยที่โค้ดเขียนคอมเมนต์ไว้ แต่ไม่มี test ล็อกไว้ | คนแก้โค้ดทีหลังจะรู้ทันทีถ้าทำให้กฎนี้หาย |
| Concurrency test (จำลองสองคำขอพร้อมกัน) | R6, R7 | บั๊กแบบ race condition ไม่โผล่ในเทสต์ปกติ | พิสูจน์ได้จริงว่ามีช่องโหว่ และพิสูจน์ว่าแก้แล้วหาย |

### อะไรที่เปลี่ยน

| # | ที่เปลี่ยน | Verification หรือ Validation | ทำไม | หลักฐาน |
|---|---|---|---|---|
| 1 | `redeemTwoFactorChallenge`: ใช้ challenge โดย `updateMany({ where: { id, consumedAt: null } })` แล้วเช็กว่าแก้ได้ 1 แถว | Verification (หาบั๊ก) | ของเดิมเช็ก `consumedAt` ก่อน แล้วค่อย `update` แยกกัน ถ้าสองคำขอเข้ามาพร้อมกัน ผ่านการเช็กทั้งคู่ และได้ token ทั้งสองใบ ทั้งที่ challenge ใช้ได้ครั้งเดียว | UT-R6 แดงกับโค้ดเดิม (ได้ 2 token) เขียวหลังแก้ |

| 3 | `redeemTwoFactorChallenge`: ตรวจ `user.status` ว่า active ก่อนออก token | Validation (ตรงตามที่ผู้ใช้และแอดมินต้องการไหม) | ขั้นรหัสผ่านเช็กสถานะแล้ว แต่ challenge อยู่ได้ 5 นาที ถ้าแอดมินระงับบัญชีระหว่างนั้น ผู้ใช้ยังได้ token ซึ่งขัดกับความตั้งใจของการระงับบัญชี | UT-R8 แดงกับโค้ดเดิม เขียวหลังแก้ |

หลังแก้ เรารันเทสต์เดิมที่เกี่ยวข้อง (`twoFactor`, `oauth`, `auth`, `bookingMaintenance` ซึ่งอ้าง 2FA) ผ่านหมด 101 ข้อ ส่วนการรัน backend ทั้งชุด (227 ไฟล์) เรารันไม่จบ เพราะช้ามาก (ไฟล์ `bookingLifecycle.test.ts` ไฟล์เดียวใช้ ~5 นาที) จึงหยุดหลังรันได้ 4 ไฟล์ ระหว่างนั้นเจอ test แดง 1 ข้อคือ `bookingAgreement.test.ts > staging the money > leaves a short hire as a single payment` เราลองคืน `auth.service.ts` เป็นเวอร์ชันเดิมแล้วรันข้อนี้ข้อเดียว ก็แดงเหมือนกัน แปลว่าแดงอยู่ก่อนแล้ว ไม่ได้เกิดจากการแก้ของเรา (ยังไม่ได้ไล่หาสาเหตุ) การตรวจผลกระทบของการแก้จึงอาศัยเทสต์ที่เรียกใช้โค้ดส่วนนี้ (101 ข้อผ่าน) ไม่ใช่การรันทั้งชุด

## สรุปเทคนิคที่ใช้ (ภาษาเรา)

| เทคนิค | ใช้ที่ไหน | เพราะอะไรถึงเลือก | มีประโยชน์กับการเทสยังไง |
|---|---|---|---|
| **Stub** | prisma / `verifyPassword` ที่ตอบค่าตามที่กำหนด | อยากเทสแค่ตรรกะล็อกอิน ไม่อยากรอฐานข้อมูลจริงหรือ argon2 ที่ช้า | คุมข้อมูลขาเข้าได้เต็มที่ เทสเร็ว (ทั้งไฟล์ใช้เวลาหลักสิบมิลลิวินาที) |
| **Spy** | `recordAudit` | อยากรู้ว่า "ระบบบันทึกอะไรลง audit" โดยไม่ขวางการทำงานจริง | ตรวจผลข้างเคียงที่ไม่ได้ return ออกมาได้ เช่น ตรวจว่าไม่มีอีเมลจริงหลุดเข้า audit |
| **Mock** | `issueToken` | บางเรื่อง "การถูกเรียก" คือตัวพฤติกรรมเอง เช่นล็อกอินไม่ผ่านต้องไม่ออก token เลย | ล็อกกฎสำคัญด้านความปลอดภัยได้ ถ้าใครเผลอออก token ในทางที่ไม่ควร test แดงทันที |
| **Fake** (ตารางจำลองในหน่วยความจำ) | challenge และ recovery code ใน UT-R | stub ธรรมดาตอบค่าเดิมทุกครั้ง แต่ race condition ต้องการสถานะที่เปลี่ยนตามเวลา | จำลอง "สองคำขอพร้อมกัน" ได้โดยไม่ต้องมีฐานข้อมูลจริงและไม่สุ่ม (ผลเหมือนเดิมทุกรอบ) |
| **Faker + seed คงที่** | ข้อมูลผู้ใช้ | ข้อมูลที่เราเขียนมือชอบซ้ำแบบเดิมจนพลาดเคสแปลก ๆ | ข้อมูลหลากหลายโดยไม่ต้องเขียนเยอะ และ seed คงที่ทำให้ test แดงแล้วรันซ้ำได้ผลเดิม |
| **Fake timers** | UT-L14, UT-R4 | อายุ 5 นาทีไม่อยากรอจริง | ทดสอบขอบเวลาได้ใน 1 มิลลิวินาที |
| **Red-green + พิสูจน์ว่า test แดงได้จริง** | เขียน UT-R6 ถึง R8 ก่อน รันกับโค้ดเดิมให้แดง แล้วค่อยแก้ | test ที่ไม่เคยแดงอาจไม่ได้เทสอะไรเลย | มั่นใจได้ว่าที่แก้ แก้ถูกจุด ไม่ใช่เขียวเพราะเทสหละหลวม |
| **Verification และ Validation** | หาจุดอ่อนจากการอ่านโค้ดและ Validation จากความต้องการของระบบ | Verification ถามว่า "เขียนถูกตามกฎของตัวเองไหม", Validation ถามว่า "ตรงกับที่ผู้ใช้ต้องการไหม" | ได้เหตุผลชัดว่าทำไมแก้แต่ละจุด ไม่ใช่แก้ตามความรู้สึก |
| **Atomic update (บอกฐานข้อมูลให้ตัดสิน)** | `updateMany` ที่มีเงื่อนไขใน WHERE | แก้ race condition ด้วยโค้ด JavaScript ฝั่งเราไม่ได้ เพราะสองคำขอเห็นข้อมูลเก่าพร้อมกัน | ทดสอบง่าย: สองคำขอพร้อมกันได้ผู้ชนะ 1 คนเสมอ |
