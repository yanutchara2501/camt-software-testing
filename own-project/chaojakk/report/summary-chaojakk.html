3. ข้อ 2.1 – ออกแบบ unit test (ฟีเจอร์ล็อกอินและ 2FA)

ทำไมเลือกฟีเจอร์นี้ เป็นด่านแรกของทุกบัญชี ถ้าพลาดคนอื่นอาจเข้าบัญชีแอดมินหรือผู้ให้เช่าได้ อีกทั้งมีตัวช่วย (collaborator) หลายตัวที่ต้องจำลอง คือฐานข้อมูล การตรวจรหัสผ่าน การออก token การบันทึก audit และการตรวจรหัส TOTP จึงใช้ stub, spy, mock ได้ครบ และมีทั้งทางสำเร็จและทางล้มเหลวหลายแบบ

โค้ดที่ทดสอบคือ platform/api/src/modules/auth/auth.service.ts (ฟังก์ชัน login และ redeemTwoFactorChallenge) ไฟล์ test คือ tests/unit/authLogin.test.ts มี 28 test

หน่วยหน้าที่ตัวช่วยที่จำลอง
loginตรวจรหัสผ่านและสถานะบัญชี แล้วออก token หรือออก challenge ถ้าเปิด 2FAprisma (stub), verifyPassword (stub), issueToken (mock), recordAudit (spy)
redeemTwoFactorChallengeแลก challenge พร้อมรหัส TOTP หรือ recovery code เป็น tokenตารางจำลองในหน่วยความจำ (fake), verifyTotp (stub), issueToken (mock)
เทคนิคออกเคสใช้ตรงไหนได้อะไร
Equivalence partitioningตัวระบุตัวตนที่ผู้ใช้พิมพ์: อีเมล, เบอร์ที่มีขีด, เลขบัตร 13 หลักที่มีขีด (UT-L9 ถึง L11)เลือกตัวแทนต่อกลุ่ม เคสน้อยแต่ครอบคลุม
Boundary value analysisอายุ challenge 5 นาที (UT-L14, UT-R4 ลองใช้หลังหมด 1 วินาที)จับ bug ที่ตัวเลขอายุเพี้ยนได้
Decision tableผลของ login ตามรหัสผ่าน / สถานะบัญชี / การเปิด 2FAเห็นว่าชุดเงื่อนไขไหนยังไม่มีเคส
State transitionchallenge: ใหม่ เป็น ใช้แล้ว หรือหมดอายุ (UT-R1 ถึง R6)บังคับให้คิดว่า "ใช้ซ้ำ" ต้องเกิดอะไร
Error guessingข้อความเหมือนกันทั้งกรณีไม่มีผู้ใช้และรหัสผิด (L6), ตรวจรหัสผ่านแม้ไม่มีผู้ใช้เพื่อให้เวลาตอบเท่ากัน (L7), audit เก็บ hash ไม่เก็บอีเมลจริง (L5)ล็อกกฎความปลอดภัยที่เดิมมีแต่คอมเมนต์ ไม่มี test
Concurrency testสองคำขอพร้อมกัน (UT-R6, R7)พิสูจน์ช่องโหว่แบบ race condition ที่ test ปกติมองไม่เห็น

4. ข้อ 2.2 – เทียบโค้ดเดิมกับโค้ดหลัง V&V

Verification ถามว่า "เขียนถูกตามกฎของตัวเองไหม" ส่วน Validation ถามว่า "ตรงกับที่ผู้ใช้ต้องการไหม" เราเทียบด้วยคำสั่ง git diff vv-original vv-improved --stat -- platform/api/src ซึ่งมีไฟล์ซอร์สที่เปลี่ยนเพียงไฟล์เดียวคือ auth.service.ts

ส่วนที่ไม่เปลี่ยน

  • ส่วนเช็กรหัสผ่าน เช็กสถานะบัญชี และออก challenge ใน login พฤติกรรมถูกต้องอยู่แล้ว (UT-L1 ถึง L16 ผ่านกับโค้ดเดิม) การเขียนใหม่มีแต่ความเสี่ยง
  • lib/totp.ts, lib/password.ts, lib/tokens.ts, router และ schema ไม่พบปัญหา และมี test เดิมคุมอยู่
  • ข้อความ error ภาษาไทยทั้งหมด เพราะฝั่ง frontend อ่านข้อความนี้โดยตรง

ส่วนที่เปลี่ยน

#สิ่งที่เปลี่ยนV หรือ Vเหตุผลหลักฐาน
1 redeemTwoFactorChallenge ใช้ challenge ด้วย updateMany({ where: { id, consumedAt: null } }) แล้วตรวจว่าแก้ได้ 1 แถว Verification ของเดิมเช็ก consumedAt แล้วค่อย update เป็นคนละคำสั่ง ถ้าสองคำขอเข้าพร้อมกันจะผ่านทั้งคู่และได้ token สองใบ ทั้งที่ challenge ใช้ได้ครั้งเดียว UT-R6 แดงกับโค้ดเดิม (ได้ 2 token) เขียวหลังแก้
2 consumeRecoveryCode เขียนกลับเฉพาะเมื่อค่าที่เก็บยังเป็นค่าที่เพิ่งอ่านมา (compare-and-swap) Verification ของเดิมอ่านรายการ ตัดรหัสออก แล้วเขียนกลับ ถ้าสองคำขอถือรหัสเดียวกันจะอ่านรายการเต็มทั้งคู่ ทำให้ recovery code ใช้ได้มากกว่า 1 ครั้ง UT-R7 แดงกับโค้ดเดิม เขียวหลังแก้
3 ตรวจ user.status ว่า active ก่อนออก token ในขั้น 2FA Validation ขั้นรหัสผ่านตรวจสถานะแล้ว แต่ challenge อยู่ได้ 5 นาที ถ้าแอดมินระงับบัญชีระหว่างนั้น ผู้ใช้ยังได้ token ซึ่งขัดกับความตั้งใจของการระงับบัญชี UT-R8 แดงกับโค้ดเดิม เขียวหลังแก้

ลำดับงานตามหลัก red-green: เขียน UT-R6 ถึง R8 ก่อนแล้วรันกับโค้ดเดิมให้เห็นว่าแดง (commit 14ffec83) จึงค่อยแก้ซอร์ส (commit 4d0b8b55) จนเขียว

6. สรุปเทคนิคที่ใช้: ใช้อะไร ทำไมเลือก ช่วยการเทสอย่างไร

เทคนิคใช้ที่ไหนเหตุผลที่เลือกประโยชน์ต่อการเทส
Stubprisma, verifyPasswordอยากทดสอบแค่ตรรกะล็อกอิน ไม่รอฐานข้อมูลจริงหรือ argon2 ที่ช้าคุมข้อมูลขาเข้าได้เต็มที่ ทั้งไฟล์รันในไม่กี่สิบมิลลิวินาที
SpyrecordAuditอยากรู้ว่าระบบบันทึกอะไรลง audit โดยไม่ขวางการทำงานจริงตรวจผลข้างเคียงที่ไม่ได้ return ได้ เช่น ไม่มีอีเมลจริงหลุดเข้า audit
